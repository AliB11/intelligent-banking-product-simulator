# سیمرغ | شبیه‌ساز محصولات اعتباری و امتیازی

**سیمرغ** یک کارگاه پژوهشی فارسی و راست‌چین برای طراحی، شبیه‌سازی، مقایسه و بهینه‌سازی محصولات اعتباری و امتیازی بانکی است. پروژه با Next.js App Router، TypeScript، PostgreSQL و Drizzle ORM ساخته شده است.

> **وضعیت و محدودیت مهم:** این نرم‌افزار نمونه‌سازی و تحلیل آموزشی است؛ سامانه بانکی عملیاتی، ابزار تصمیم اعتباری واقعی یا مشاوره حقوقی/مالی نیست. جمعیت و رفتار مشتریان مصنوعی‌اند، ضرایب رفتاری و نکول فرضی و قابل تنظیم‌اند، و گزارش پژوهشی جایگزین بررسی آخرین بخشنامه‌ها نیست. این پروژه احراز هویت و مجوزدهی ندارد؛ آن را بدون افزودن کنترل دسترسی، محدودسازی نرخ و بازبینی امنیتی روی اینترنت عمومی عرضه نکنید. هیچ داده شخصی واقعی مشتری را وارد نکنید.

## قابلیت‌ها

- ۱۶ الگوی آغازین با الهام از محصولات ایران: مرابحه، کارت اعتباری، BNPL، وام خرد، قرض‌الحسنه، جعاله، اجاره به شرط تملیک، خط کسب‌وکار، اعتبار طلامحور، امتیاز پول–زمان و باشگاه وفاداری.
- طراح زنده محصول و سازنده ایده خلاقانه با seed تصادفی امن در مرورگر.
- شبیه‌سازی مشتری مصنوعی با اشتغال، درآمد، منطقه، رتبه اعتباری ۰ تا ۹۰۰، سابقه اعتباری، سپرده، وثیقه و رفتار دیجیتال.
- مدل‌سازی تقاضا، سیاست اعتباردهی و DTI، احتمال نکول قابل توضیح، زیان مورد انتظار، وام‌دهی امتیازی و اقتصاد پاداش.
- شبیه‌سازی مونت‌کارلو با شوک نظام‌مند واسیچک، منحنی سررسید نکول و زمان‌بندی جذب باس.
- گزارش سود و زیان، بازده واقعی پس از تورم، APR، NPL، VaR، سرمایه IRB، شمول مالی و شکاف دسترسی دهک‌های درآمدی.
- بررسی قواعد پیکربندی‌شده مقرراتی و تطابق عقد با موضوع؛ همراه با هشدارها و پیشنهادهای قابل اعمال.
- قیمت‌گذاری به تفکیک رتبه اعتباری، تست استرس ۷ سناریو، تحلیل حساسیت، بهینه‌ساز و مرز پارتو.
- آزمایشگاه ALM و طراح معکوس پله‌ها: جریان نقد، کسری نقدینگی، هزینه تمام‌شده مشتری و مقایسه اجراهای ذخیره‌شده.
- شبیه‌ساز سفر ۶ پرسونا، مقایسه تا ۴ محصول، گزارش قابل چاپ و خروجی JSON.
- ذخیره محصول و تاریخچه شبیه‌سازی در PostgreSQL؛ رابط کاملاً فارسی و RTL.

## پیش‌نیازها

- Node.js نسخه ۲۰.۹ یا جدیدتر (CI روی Node.js 22 اجرا می‌شود)
- npm
- PostgreSQL نسخه ۱۴ یا جدیدتر

### اجرای محلی با Docker

```bash
git clone <آدرس-مخزن>
cd <پوشه-پروژه>
cp .env.example .env

docker run --name simorgh-postgres \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=app_db \
  -p 5432:5432 \
  -d postgres:16

npm ci
npx drizzle-kit push
npm run dev
```

سپس `http://localhost:3000` را باز کنید. در اجرای نخست، برنامه جداول اصلی را ایجاد می‌کند و در پایگاه داده خالی پنج الگوی آغازین را می‌سازد. اجرای `drizzle-kit push` برای همگام‌سازی صریح schema توصیه می‌شود.

برای توقف پایگاه داده Docker:

```bash
docker stop simorgh-postgres
```

### متغیرهای محیطی

| متغیر | اجباری | توضیح |
|---|---:|---|
| `DATABASE_URL` | بله | رشته اتصال PostgreSQL؛ نمونه محلی در `.env.example` قرار دارد. |

فایل `.env` عمداً در Git نادیده گرفته می‌شود. برای محیط‌های واقعی از secret manager میزبان استفاده کنید و هیچ رمز، URL خصوصی یا داده محرمانه‌ای را commit نکنید.

## فرمان‌های توسعه و کنترل کیفیت

```bash
npm ci
npm run dev
npx next typegen
npm run lint
npm run typecheck
npm test
npm audit --omit=dev
npm run build
npm run start
```

برای اجرای محلی، `DATABASE_URL` را در `.env` تنظیم کنید. در گردش‌کار GitHub Actions گیت‌های تست موتور، تست یکپارچگی PostgreSQL، audit وابستگی production، lint، تولید typeهای Next.js، TypeScript، build، HTTP و مرورگر تعریف شده‌اند. نتیجه اجرای محلی با وضعیت اجرای واقعی CI روی GitHub یکسان نیست.

برای پیش‌نمایش پشت reverse proxy، سرور را با `npm run dev -- --hostname 0.0.0.0` یا `npm run start -- --hostname 0.0.0.0` اجرا کنید؛ درخواست‌های مرورگر از URLهای نسبی استفاده می‌کنند. این تنظیم شبکه جایگزین حفاظت دسترسی نیست.

## کاربرد

1. از داشبورد به «کارگاه طراحی» بروید و یک الگو انتخاب کنید یا محصولی از صفر بسازید.
2. پارامترهای محصول، قرارداد، نرخ/کارمزد، مبلغ و دوره، تضامین، سیاست ریسک و هزینه منابع را ویرایش کنید.
3. پیش‌نمایش زنده و گزارش انطباق را بررسی کنید؛ پیشنهادهای دستیار را در صورت نیاز اعمال کنید.
4. محصول را ذخیره و وارد آزمایشگاه آن شوید.
5. اندازه بازار، افق، تعداد تکرار مونت‌کارلو و سناریوی کلان را تعیین کنید؛ تست استرس، حساسیت و بهینه‌ساز را جداگانه اجرا کنید.
6. در صورت نیاز گزارش را چاپ/ذخیره به PDF یا خلاصه پیکربندی را به JSON صادر کنید.

### واحدهای شبیه‌سازی

- مبالغ ورودی مشتری و محصول: **میلیون تومان**.
- درآمد/هزینه تجمیعی سبد: **میلیارد تومان** (در ارقام بزرگ «همت»).
- اندازه بازار در UI تعداد مشتری بالقوه است؛ ضریب مقیاس، نمونه مصنوعی را به آن بازار تعمیم می‌دهد.
- بذر ثابت در تنظیمات شبیه‌سازی برای بازتولیدپذیری وجود دارد؛ محصول تصادفی از مولد تصادف رمزنگارانه مرورگر seed می‌گیرد.

## APIهای اصلی

| مسیر | روش | کاربرد |
|---|---|---|
| `/api/health` | `GET` | بررسی اتصال پایگاه داده |
| `/api/products` | `GET`, `POST` | فهرست/ساخت محصول |
| `/api/products/:id` | `GET`, `PUT`, `DELETE` | مشاهده، ویرایش و حذف محصول |
| `/api/simulate` | `POST` | اجرای مونت‌کارلو و ثبت نتیجه برای محصول ذخیره‌شده |
| `/api/analyze` | `POST` | `mode`: یکی از `stress`, `sensitivity`, `optimize` |
| `/api/alm` | `POST` | تحلیل ALM، طراح معکوس و ثبت اختیاری با `save:true` |

نمونه اجرای شبیه‌سازی:

```bash
curl -X POST http://localhost:3000/api/simulate \
  -H 'Content-Type: application/json' \
  -d '{"productId":1,"params":{"customers":4000,"runs":24,"scenario":"base","horizon":36}}'
```

### قرارداد ورودی، نسخه و تاریخچه

- بدنه باید یک شیء `application/json` با حداکثر **۶۵٬۵۳۶ بایت UTF-8** باشد. Origin بین‌سایتی رد می‌شود؛ کلاینت‌های CLI می‌توانند Origin نداشته باشند، پس این کنترل **احراز هویت نیست**.
- در شبیه‌سازی/تحلیل فقط یکی از `config` یا `productId` را بفرستید. در ALM دقیقاً یکی از `config`، `productId` یا `templateKey` پذیرفته می‌شود؛ نام قدیمی `product` نیز برای سازگاری پشتیبانی می‌شود. `save:true` فقط همراه `productId` مجاز است.
- پیکربندی با whitelist و کران‌های عددی canonical می‌شود؛ پاسخ ساخت/ویرایش، `config` پذیرفته‌شده و `configVersion` را برمی‌گرداند. هشدارهای مقرراتی الزاماً به معنی رد یا اصلاح خودکار پیکربندی نیستند.
- برای ویرایش، نسخه خوانده‌شده را همراه بدنه `{"config":{...},"configVersion":1}` در `PUT /api/products/:id` بفرستید. نسخه قدیمی پاسخ **409** می‌گیرد؛ ابتدا محصول را دوباره دریافت و تغییرات را بازبینی کنید، نه اینکه کورکورانه تکرار کنید. کلاینت قدیمی بدون `configVersion` پشتیبانی می‌شود، اما تضمین کشف ویرایش کهنه کلاینت را ندارد.
- اجراهای ذخیره‌شده snapshot پیکربندی، نسخه محصول، نسخه موتور و ورودی‌های بازتولیدپذیر را نگه می‌دارند. پس از تغییر محصول/موتور، نتیجه قبلی در تاریخچه می‌ماند ولی به‌عنوان نتیجه جاری نمایش داده نمی‌شود. `latest` داشبورد فقط از مونت‌کارلوی معتبر می‌آید، نه آخرین تحلیل از هر نوع.
- در موتور `simorgh-2026-10-10.2` نسبت‌های `raroc`، `rarocCredit`، `rarocLiquidity`، `roa` و `nim` می‌توانند **`null`** باشند: سرمایه/دارایی مبنای مثبت ندارند یا برای باشگاه وفاداری کاربرد ندارند. `null` را به صفر، بازده بی‌نهایت یا «بهترین محصول» تبدیل نکنید. RAROC نقدینگی فقط با سرمایه نقدینگی مثبت ممکن است مستقل از RAROC اعتباری قابل محاسبه باشد. در خروجی بهینه‌ساز، `baseline.feasible` و `best.feasible` وضعیت امکان‌پذیری مدل را نشان می‌دهند؛ وقتی `best.feasible` نادرست است، پیشنهاد قابل اعمالی وجود ندارد.

### کران‌های اصلی پارامترها

| پارامتر مونت‌کارلو | دامنه API و آزمایشگاه |
|---|---|
| مشتری نمونه | ۵۰۰ تا ۱۰٬۰۰۰ |
| تعداد اجرا | ۱ تا ۶۰ |
| افق | ۱۲ تا ۶۰ ماه |
| نرخ مؤثر رقبا | ۵ تا ۶۰ درصد |

دامنه ALM مستقل است: افق ۱۲ تا ۱۲۰ ماه، سهم بازار ۰٫۱ تا ۵۰ درصد و seed تا ۲٬۱۴۷٬۴۸۳٬۶۴۷. سقف ورودی به‌تنهایی جلوی فشار درخواست‌های متعدد را نمی‌گیرد؛ APIها همچنان به احراز هویت و محدودسازی نرخ/هم‌زمانی نیاز دارند.

## فرض‌ها و اعتبار مدل

- روش‌های IRB، واسیچک و باس در این پروژه ساده‌سازی شده‌اند؛ پیاده‌سازی، مدل تأییدشده سرمایه‌ای یا اعتبارسنجی مستقل نیست.
- توزیع درآمد، نرخ نکول، اثر وثیقه، تقاضا و پاسخ قیمتی برای **مقایسه طراحی‌ها** ساخته شده‌اند، نه پیش‌بینی عملکرد بانک واقعی.
- قواعد انطباق در کد یک چک‌لیست تقریبی‌اند. تفسیر شرعی، حقوقی و مقرراتی باید به تأیید متخصص واجدصلاحیت و متن رسمی و به‌روز برسد.
- نرخ‌ها و اطلاعات بازار در `RESEARCH.md` با تاریخ مرجع ذکر شده‌اند و ممکن است تغییر کنند؛ پیش از استفاده تجاری، منبع رسمی بانک مرکزی/بانک مربوطه را دوباره بررسی کنید.
- شبیه‌ساز در حال حاضر اتصال به ICS، بانک، سامانه پرداخت، سامانه وثیقه یا API خارجی ندارد.
- قرض‌الحسنه در موتور اصلی با جدول مانده‌کاه مدل می‌شود، ولی ALM از کارمزد سالانه ثابت روی اصل استفاده می‌کند؛ این دو خروجی بدون تعیین سیاست عقد واحد قابل هم‌ارز دانستن نیستند.
- انقضای امتیاز وام امتیازی اثر فرضی بر تقاضاست؛ در وفاداری بر تقاضا/مصرف‌نشدن امتیاز هم اثر دارد. هیچ‌یک دفترکل عملیاتی انقضای امتیاز نیست. فیلد `incomeGrowth` در رشد درآمد مشتری به‌کار نرفته و helper ادغام KPIهای ALM در مسیر جاری فراخوانی نمی‌شود.
- LCR/NSFR، سرمایه و امتیاز سلامت شاخص‌های آموزشی‌اند؛ عنوان‌های سلامت، مجوز عرضه محصول نیستند. تعداد محدود اجرای مونت‌کارلو نیز تضمین دقت VaR یا پیش‌بینی زیان واقعی نیست.

## بازبینی و تست‌های رگرسیون

گزارش جاری اصلاحات، شدت یافته‌ها، شواهد اجرا و محدودیت‌های باقی‌مانده در [بازبینی لایه‌ای عمیق — ۲۰۲۶-۱۰-۱۰](docs/LAYERED-AUDIT-2026-10-10.md) آمده است. گزارش‌های [فنی و UX مرحله قبل](docs/AUDIT-2026-10-09.md) و [بازبینی قبلی فرمول‌ها](docs/AUDIT-2026-10-10.md) برای سابقه نگه داشته شده‌اند؛ اعداد آن‌ها نتیجه موتور جاری نیستند.

- `npm test`: تست‌های موتور مالی، رنگ/کنتراست و مرز ورودی API، بدون نیاز به پایگاه داده.
- `TEST_DATABASE_URL=... npm run test:db`: تست نسخه‌ها، هم‌زمانی، snapshot، تاریخچه و بازیابی اتصال، فقط روی PostgreSQL دورریختنی. بدون متغیر صریح `TEST_DATABASE_URL` عمداً خطا می‌دهد و به `DATABASE_URL` fallback نمی‌کند.
- `SMOKE_BASE_URL=http://127.0.0.1:3000 npm run test:smoke`: بررسی HTTP روی سرور روشن با **پایگاه داده آزمایشی**؛ fixtureهای خودش را می‌سازد و حذف می‌کند.
- پس از `npx playwright install --with-deps chromium`، فرمان `SMOKE_BASE_URL=http://127.0.0.1:3000 npm run test:browser` تعامل واقعی، hydration، موبایل، کنسول و axe را بررسی می‌کند. Chromium موجود را می‌توان با `BROWSER_EXECUTABLE_PATH` مشخص کرد. این تست نیز محصول آزمایشی ایجاد/حذف می‌کند؛ تأیید رسمی WCAG نیست.
- `npm audit --omit=dev`: بررسی وابستگی‌های production؛ `npm audit` کامل شامل ابزارهای توسعه نیز هست. موفقیت audit production به معنی امن‌بودن معماری برنامه نیست.
- پیش از انتشار عمومی، الزامات [امنیت](SECURITY.md) را اجرا کنید؛ این نمونه هنوز سامانهٔ بانکی چندکاربرهٔ آمادهٔ production نیست.
